## 一、全局账单（Global Bill）

### 1.1 定位与展示范围

全局账单是用户维度的**全渠道交易流水**，展示当前用户作为付款方或收款方参与的**所有资金交易**，覆盖余额、银行卡、花呗三种资金渠道。

**核心原则**：一笔交易只要用户是任一方（付款或收款），就在其全局账单中出现。

### 1.2 展示规则梳理

#### 1.2.1 余额/银行卡收付款

| 场景 | 付款方账单展示 | 收款方账单展示 |
|---|---|---|
| A用余额给B转账100元 | 支出 -100元，标题"转账"，副标题"转给B" | 收入 +100元，标题"转账"，副标题"来自A" |
| A用银行卡给B转账100元 | 支出 -100元，标题"银行卡转账"，资金渠道标签"银行卡" | 收入 +100元，标题"转账收款"，资金渠道标签"银行卡" |
| A扫B的码用余额付款100元 | 支出 -100元，标题"扫码支付"，副标题"付给B" | 收入 +100元，标题"扫码收款"，副标题"来自A" |
| A扫B的码用银行卡付款100元 | 支出 -100元，标题"银行卡扫码支付"，渠道标签"银行卡" | 收入 +100元，标题"扫码收款"，渠道标签"银行卡" |

#### 1.2.2 花呗收付款

| 场景 | 付款方账单展示 | 收款方账单展示 | 花呗专属账单展示 |
|---|---|---|---|
| A用花呗扫B的码付款100元 | 支出 -100元，标题"花呗消费"，副标题"付给B"，渠道标签"花呗" | 收入 +100元，标题"扫码收款"，副标题"来自A（花呗）"，渠道标签"花呗" | **仅付款方A显示**："花呗消费 -100元"（因为A需要还款） |

**规则说明**：
- 花呗消费（`CREDIT_PAY`）不扣减付款方余额，但占用信用额度，付款方需要还款，因此付款方全局账单和花呗账单均显示。
- 收款方B的余额实际增加了100元（由信用应收资产对应），因此B的全局账单显示为收入。但B的花呗账单不显示（B没有花呗负债）。
- 花呗还款（`CREDIT_REPAY`）：仅还款方显示，标题"花呗还款"，支出金额，渠道标签"花呗"。

#### 1.2.3 充值与提现

| 场景 | 展示 |
|---|---|
| 银行卡充值500元到账户余额 | 收入 +500元，标题"银行卡充值"，渠道标签"银行卡" |
| 提现200元到银行卡 | 支出 -200元，标题"银行卡提现"，渠道标签"银行卡" |

**说明**：当前扫码支付不提供退款功能，全局账单不涉及退款类交易展示。

### 1.3 账单列表项 UI 字段设计

每个列表项包含以下字段：

| 字段 | 说明 | 取值逻辑 |
|---|---|---|
| **交易类型图标** | 左侧圆形图标，区分业务类型 | 转账→`transfer`图标；扫码支付→`qr`图标；花呗消费→`huabei`图标；充值→`wallet`图标；提现→`card`图标；还款→`huabei`图标 |
| **主标题** | 交易类型名称 | 根据 `business_type` + `funding_source` + 用户角色（付款/收款）组合生成：如"转账"、"扫码支付"、"花呗消费"、"扫码收款"、"转账收款"、"银行卡充值"、"银行卡提现"、"花呗还款" |
| **副标题/交易对象** | 对方用户脱敏信息 | 付款方视角：`转给 {收款人昵称}`；收款方视角：`来自 {付款人昵称}`；无对方信息时显示资金来源说明，如"银行卡充值" |
| **金额** | 带正负号的金额 | 收入显示 `+¥XX.XX`（绿色），支出显示 `-¥XX.XX`（默认色）。金额从 `ledger_entry.amount_fen` 取，方向由分录所属账户的借贷方向决定 |
| **交易时间** | 交易完成时间 | 取 `fund_transaction.created_at` 或 `ledger_entry.created_at`，格式 `MM-DD HH:mm`（当天显示 `HH:mm`，跨年显示 `YYYY-MM-DD`） |
| **交易状态** | 当前交易状态 | `SUCCESS`→不显示（默认成功）；`PROCESSING`→橙色"处理中"标签；`MANUAL_REVIEW`→黄色"审核中"标签；`CANCELLED`→灰色"已取消"标签；`REVERSED`→灰色"已冲正"标签 |
| **资金渠道标签** | 小标签显示资金来源 | `BALANCE`→不显示（默认）；`BANK_CARD`→蓝色"银行卡"标签；`MINI_CREDIT`→紫色"花呗"标签；`SYSTEM_ISSUANCE`→不显示（充值场景已通过标题体现） |
| **交易后余额**（可选） | 该笔交易后的账户可用余额 | 取 `ledger_entry.balance_after_fen`，仅在余额变动类交易中显示，格式 `余额 ¥XX.XX`，灰色小字 |

### 1.4 数据来源与查询策略

- **主数据源**：`ledger_entry` 表（`ledger_db`），通过 `GET /api/v1/accounts/me/entries` 接口获取，已包含 `balance_after_fen` 展示列。
- **补充数据源**：银行卡充值/提现和银行卡出资付款方扣卡记录通过 `fund_transaction` 表（`business_db`）补充投影；银行卡出资转账/扫码的收款方余额增加必须写入账户中心账本分录，不能依赖付款方银行卡流水补齐。现有 `Transactions` 页面的 `loadBankCardTransactions()` 函数仅负责付款方银行卡交易补充。
- **花呗账单**：通过 `GET /api/v1/credit/bills` 和 `GET /api/v1/credit/purchases` 获取，在花呗专属视图中单独展示。
- **分页策略**：游标分页，默认每页 50 条，最大 100 条，按 `created_at` 倒序。

## 二、钱包页"余额变动明细"

### 2.1 业务边界分析

#### 2.1.1 与全局账单的差异

| 维度 | 全局账单 | 余额变动明细 |
|---|---|---|
| **定位** | 用户所有交易的全景视图 | 聚焦直接影响可用余额的流水 |
| **包含的交易类型** | 全部（含花呗消费等不直接影响余额的交易） | 仅余额变动类交易（见下表） |
| **花呗消费** | 包含（付款方和收款方均显示） | **不包含**（花呗消费不扣减余额，只占用额度） |
| **花呗还款** | 包含 | **包含**（还款扣减余额） |
| **入口位置** | 首页快捷区 / 底部导航 | 钱包页余额卡片下方 |

#### 2.1.2 余额变动明细包含的交易类型

以下交易类型**直接影响账户可用余额**，纳入余额变动明细：

| 业务类型 | funding_source | 对余额的影响 | 展示标题 |
|---|---|---|---|
| `TRANSFER`（转账付款） | `BALANCE` | 余额减少 | 转账支出 |
| `TRANSFER`（转账收款） | `BALANCE` | 余额增加 | 转账收入 |
| `TRANSFER`（转账付款） | `BANK_CARD` | 余额增加（收款方） | 转账收入（银行卡） |
| `QR_PAY`（扫码付款） | `BALANCE` | 余额减少 | 扫码支付 |
| `QR_PAY`（扫码收款） | `BALANCE` | 余额增加 | 扫码收款 |
| `QR_PAY`（扫码收款） | `BANK_CARD` | 余额增加 | 扫码收款（银行卡，来自收款方账本分录） |
| `RECHARGE`（充值） | `SYSTEM_ISSUANCE` | 余额增加 | 银行卡充值 |
| `BANK_CARD_WITHDRAW`（提现） | — | 余额减少 | 银行卡提现 |
| `CREDIT_REPAY`（花呗还款） | `BALANCE` | 余额减少 | 花呗还款 |

**明确排除的交易类型**：

| 业务类型 | 排除原因 |
|---|---|
| `CREDIT_PAY`（花呗消费） | 不扣减余额，只占用信用额度；收款方余额增加已由其对应的 `QR_PAY`/`TRANSFER` 入账体现 |

### 2.2 UI 布局设计

#### 2.2.1 钱包页改造（`/h5/wallet`）

**改造内容**：移除底部"资金渠道说明"区域（`.wallet-tips`），替换为"余额变动明细"入口卡片。具体布局参见上方钱包页面改造效果图。

**入口卡片设计细节**（参见钱包页面改造效果图）：
- 样式：与银行卡列表卡片风格一致，白色圆角卡片，左侧图标 + 文字 + 右侧箭头
- 图标：使用 `receipt` 或 `list` 图标，蓝色圆形背景
- 文案：主标题"余额变动明细"，副标题"查看余额收支流水"
- 点击跳转：`/h5/wallet/balance-entries`

#### 2.2.2 余额变动明细页面（`/h5/wallet/balance-entries`）

**页面整体结构**：参见上方余额变动明细页面效果图。页面从上到下依次为：顶部余额卡片 → 筛选胶囊栏 → 月份分组流水列表。

**各区域详细设计**：

##### （1）顶部余额卡片

| 元素 | 设计 | 说明 |
|---|---|---|
| 标题 | "当前余额" | 灰色小字，14px |
| 余额数值 | `¥12,345.67` | 大号字体，32px，支持掩码切换 |
| 掩码切换 | 眼睛图标按钮 | 点击切换显示/隐藏，默认显示，掩码为 `****` |
| 账户号 | `62****7890` | 灰色小字，12px，脱敏展示 |
| 背景 | 与钱包页顶部一致的柔渐变 | 保持视觉连贯性 |

**不展示总资产**：遵循 PRD 13.5 要求，"余额与信用额度分区展示，不汇总为总资产"。

##### （2）筛选与排序交互

**筛选方式**：单行横向滑动胶囊按钮，单选模式。

| 筛选项 | 筛选逻辑 |
|---|---|
| 全部 | 不过滤，展示所有余额变动记录 |
| 收入 | `direction = 'IN'` |
| 支出 | `direction = 'OUT'` |
| 充值提现 | memo 含"充值"或"提现" |
| 转账 | memo 含"转账" |
| 扫码 | memo 含"扫码"或"支付"或"收款" |
| 花呗还款 | memo 含"花呗还款" |

**说明**：当前扫码支付不提供退款功能，筛选项中不包含"退款"。

**排序**：固定按时间倒序（最新在前），不提供排序切换选项（符合用户查看最新流水的习惯）。

**筛选交互细节**：
- 胶囊按钮横向排列，超出屏幕宽度时可左右滑动
- 选中项背景色为品牌色（渐变蓝），文字白色
- 未选中项背景为浅灰色，文字深灰色
- 切换筛选时列表即时刷新，保留当前滚动位置

##### （3）流水列表项 UI 结构

每个列表项为单行布局：左侧圆形图标，中间主标题+副标题+时间余额，右侧金额。具体样式参见效果图中的流水行。

| 元素 | 样式 | 说明 |
|---|---|---|
| 图标 | 左侧圆形背景，16px 图标 | 充值→`wallet`；提现→`card`；转账→`transfer`；扫码→`qr`；花呗还款→`huabei` |
| 主标题 | 15px，深色 | 如"银行卡充值"、"转账收入"、"扫码支付"、"花呗还款" |
| 副标题 | 13px，灰色 | 交易对象或补充说明，如"来自 小王"、"付给 便利店"、"工商银行 ****1234" |
| 金额 | 15px，右对齐 | 收入绿色 `+¥XX.XX`，支出默认色 `-¥XX.XX` |
| 时间 | 12px，灰色 | `MM-DD HH:mm` 格式 |
| 交易后余额 | 12px，灰色 | `余额 ¥XX.XX`，与时间同行，用 `·` 分隔 |

**分组**：按月份分组，每组顶部显示月份标题（如"2026年8月"），组内按时间倒序排列。

**空状态**：无记录时显示空状态图标 + "暂无余额变动记录" + "充值、转账、收款完成后将在这里展示"。

**分页**：下拉加载更多（触底自动加载），每页 20 条。

### 2.3 数据查询策略

余额变动明细页面的数据来源：

1. **主数据源**：`GET /api/v1/accounts/me/entries`（账本分录），已包含 `balance_after_fen`。
2. **补充数据源**：银行卡充值/提现/出资交易投影（与现有 `Transactions` 页面的 `loadBankCardTransactions()` 逻辑一致）。
3. **过滤逻辑**：在前端或后端排除 `CREDIT_PAY` 类型交易（花呗消费不影响余额）。

**建议后端支持**：后续可在 `GET /api/v1/accounts/me/entries` 接口增加 `business_type` 过滤参数，由后端直接排除 `CREDIT_PAY`，减少前端过滤开销。MVP 阶段可先在前端过滤。

- 输入栏悬浮于内容之上，消息列表底部预留足够 padding，滚动时消息内容不被输入框遮挡。

## 六、2026-08-11 补充设计：个人扫码银行卡付款与三页账单边界

### 6.1 个人扫码付款方式

个人收款码、固定金额收款请求和 C2C 个人收款订单的付款方式调整为“账户余额 + 银行卡”。个人扫码给个人付款不得使用 Mini 花呗，前端不展示花呗入口，后端确认接口仅接受 `BALANCE` 与 `BANK_CARD`；客户端篡改提交 `MINI_CREDIT` 时必须返回资金来源不允许的业务错误。

选择 `BANK_CARD` 时，确认请求和支付请求都必须携带本人银行卡 `cardId`，并将 `cardId` 纳入确认摘要，防止同一个确认令牌被替换成另一张卡或另一种资金来源使用。银行卡付款受理为 `TRANSFER` 主单，资金从银行卡虚拟余额扣减，收款方账户余额入账。

### 6.2 账单页

账单页只保留“全部、收入、支出”三个筛选项，不再承载分析功能。账单展示用户参与的所有成功资金交易，包含余额、银行卡和花呗相关交易；银行卡直接出资的转账、扫码付款虽然不改变付款方账户余额，也必须进入账单。

### 6.3 钱包最近明细与余额明细页

钱包页新增最近 5 条“余额明细”，筛选项同样只保留“全部、收入、支出”，点击“查看全部”进入完整余额明细页。余额明细只展示直接改变账户可用余额的记录：余额转账/扫码、收款入账、银行卡充值提现、花呗还款；排除银行卡直接出资的付款方支出和花呗消费付款方信用分录。

### 6.4 银行卡出资收款方明细修正规则

银行卡出资转账/扫码成功时，付款方 A 的余额账户不变化，A 的全局账单通过银行卡流水展示“银行卡转账扣款/银行卡扫码支付”；收款方 B 的余额账户真实增加，必须由 account-center 在同一 Seata 全局事务中注册外部出资 `LEDGER` 分支，生成“系统外部清算借方 + B 用户余额贷方”的平衡凭证。终态发布前必须验证银行卡扣减、B 收款入账和账本过账都完成，避免出现“B 余额正确变化但余额明细没有收款记录”的情况。
