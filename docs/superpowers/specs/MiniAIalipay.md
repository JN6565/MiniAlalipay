## 🎯 选题背景

支付是金融的基石，而**转账**是支付最核心的场景。
 在高并发、分布式架构下，如何保证“钱不少、账不乱”是永恒的挑战：

- **数据一致性**：A 扣款成功，B 入账失败，钱去哪了？
- **事务复杂性**：跨服务、跨数据库的调用，如何保证原子性？
- **交互新范式**：用户不再想点击繁琐的表单，只想对 AI 说“转给小王 50 块买咖啡”，系统能否理解并安全执行？

**你的任务**：
 构建一个“迷你支付宝”**系统，不仅实现核心的**转账支付闭环，更要打造一条**生产级的 AI 助理工程链路**：

- **基础链路**：搭建账户、用户、业务三大中心，**必须使用分布式事务框架（如 DTX/TCC）**保障资金一致性。
- **智能化链路（AI Agent）**：构建支付宝 AI 助理，支持**多轮对话、上下文记忆、工具调用、人工确认、链路追溯**。
- **数据监控（全链路）**：实现实时/离线数据大盘，监控系统运行状态。

**强制架构要求**：

1. **双端交互**：传统前端页面（Web/App） + AI Talk 对话界面，功能对齐。
2. **分布式事务**：转账必须使用 TCC/Saga 等模式，严禁本地事务模拟。
3. **Agent 工程化**：AI 助理必须支持**工具定义（MCP/HTTP）、上下文管理、执行链路日志**。
4. **安全合规**：AI 不能绕过支付密码和风控校验，资金操作必须二次确认。

## 📋 核心功能建议

### 1. 基础业务链路

**A. 用户中心 (User Center)**

- **注册/登录**：支持用户名/密码注册，自动开立资金账户（送 10000 虚拟金）。
- **支付密码**：6 位数字密码，转账时必须校验（加密存储/传输）。
- **智能查询**：支持根据登录名/昵称查询用户信息（供 AI 确认收款人）。

**B. 账户中心**

- **开户/销户**：用户注册即开户，支持复式记账（借/贷）。
- **余额查询**：高并发下余额准确查询（注意缓存一致性）。
- **明细查询**：记录每一笔转账流水（时间、对象、金额、状态）。

**C. 业务中心 **

- 分布式转账

  ：

  - **必须使用分布式事务框架**（如 Seata/TCC、Saga、本地消息表）。
  - 实现 Try-Confirm-Cancel 流程，确保“A 扣款成功，B 入账失败”时能自动回滚。
  - **幂等性设计**：防止网络重试导致重复扣款。

- **状态机管理**：转账单据状态流转（创建→处理中→成功/失败→已冲正）。

### 2. 智能化链路

**A. 多轮对话与上下文管理**

- **意图识别**：识别“转账”、“查余额”、“查账单”、“查用户”等意图。

- 槽位填充

  ：从对话中提取关键信息（收款人、金额、备注）。

  - 例：用户说“转给小王”，AI 追问“转多少钱？”；用户说“50 块”，AI 补全槽位。

- 上下文记忆

  ：

  - 例：用户问“余额多少？” → AI 答“1000 元” → 用户说“那转 500 给小李”，AI 能理解“那”指代余额操作。
  - 例：用户说“只看昨天的”，AI 能修正上一轮账单查询的时间范围。

**B. 工具调用与安全确认**

- **能力封装**：将后端接口封装为 AI 可调用的 Tool（基础：HTTP；优秀：MCP Server）。

- 资金操作确认

  ：

  - 涉及转账时，AI **必须**生成确认卡片：“确认向小王转账 500 元吗？请输入支付密码。”
  - **严禁**AI 绕过密码直接调用转账接口。

- **异常处理**：接口失败（如余额不足）时，AI 需解释原因并引导用户（“余额不足，是否充值？”）。

**C. 链路可追溯 (Traceability)**

- 执行日志

  ：记录每一次 Agent 调用的完整链路：

  - 用户输入 → 意图识别结果 → 提取的槽位 → 调用的 Tool 及入参 → 接口返回 → 最终回复。

- **问题定位**：当出现错误时，能通过日志快速定位是“意图识别错”、“参数提取错”还是“接口调用错”。

### 3. 数据监控与大盘

**A. 实时指标大盘**

- **分钟级监控**：支付创建/成功/失败笔数、金额、用户数（区分转账/充值）。
- **可视化曲线**：使用监控工具（如 AntMonitor/Grafana）展示实时流量波形。

**B. 离线业务报表 (T+1)**

- **核心指标**：日登录成功率、注册转化、支付成功率、金额不足失败占比。
- **技术实现**：基于日志（严禁直连业务 DB）通过离线链路（如 MaxCompute+Flink）加工数据。

### 4. 传统前端页面

- **功能对齐**：注册、登录、转账表单、余额查询、明细列表、资产分析图表。
- **体验要求**：界面整洁，操作流畅，异常提示清晰。
- **双端互通**：前端页面做的转账，AI 助理能查到；AI 助理做的转账，前端页面能显示。

## 🚀 技术挑战方向

### 方向 A：MCP Server 标准化架构

- **完整封装**：将转账、查询等能力封装为符合 **MCP Protocol** 的 Server。
- **工具发现**：Agent 支持动态发现 MCP Server 上的工具，无需硬编码。
- **权限控制**：在 MCP 层实现细粒度权限（如：查询类工具无需确认，转账类工具需二次确认）。

### 方向 B：极致的事务一致性

- **故障注入**：模拟网络分区、DB 宕机，证明 TCC/Saga 能自动恢复，数据零丢失。
- **防悬挂设计**：解决 TCC 模式下的“空回滚”和“悬挂”问题。
- **对账系统**：实现独立的“证 - 账 - 实”核对脚本，自动发现并修复差异。

### 方向 C：Agent 高级能力

- **上下文压缩**：多轮对话后，对历史记忆进行摘要/筛选，降低 Token 消耗。
- **用户记忆 (Memory)**：沉淀用户偏好（如“习惯转给小王”、“喜欢整额转账”），提供个性化服务。
- **智能纠错**：用户说“转给小王 500 万”（明显异常），AI 主动风险提示并要求二次确认。

### 方向 D：全链路质量保障

- **自动化测试**：接口自动化覆盖率>30%，包含异常场景（余额不足、密码错误、网络超时）。
- **AI 生成用例**：使用大模型生成测试用例或单元测试代码，并验证有效性。
- **性能优化**：针对高并发场景（如热点账户），设计多级缓存或异步处理方案。

## ⏱️ 工期

**MVP 范围**：

- **后端**：完成注册、登录、转账（本地事务即可，但结构要清晰）。
- **前端**：完成基础web页面，能手动转账。
- **AI**：实现基于 HTTP 的简单对话，能听懂“转账”并调用接口（可不做二次确认，但要有提示）。
- **目标**：跑通“说话→转账→成功”的最小闭环。

## 🏆 建议重点考虑

| 维度               | 评分关键点                                                   |
| ------------------ | ------------------------------------------------------------ |
| **分布式事务设计** | 方案选型是否合理？是否真正解决了 Consistency 问题？有无补偿/回滚机制？ |
| **AI Agent 集成**  | 对话是否自然？是否成功调用后端接口？MCP 封装是否规范（加分项）？ |
| **系统安全性**     | 是否有幂等性设计？支付密码是否加密？有无防注入/防重放措施？  |
| **双端体验**       | Web 端是否易用？AI 端是否智能？两者数据是否一致？            |
| **监控与运维**     | B 端监控是否实时？能否发现并处理异常订单？                   |

## 💡 Tips

1. **事务是生命线**：宁可功能少做，也要保证转账逻辑的**数据一致性**。如果钱对不上，项目直接不及格。
2. **AI 不是万能钥匙**：AI 助理只是**交互层**，真正的资金校验、事务控制必须在**后端**完成。别把逻辑全写在 Prompt 里。
3. **日志是关键**：一定要记录详细的**Trace Log**（上下文、工具调用、入参出参）。这是排查 AI“幻觉”或“乱调用”的唯一依据。
4. **MCP 是加分项**：如果时间允许，尝试将后端能力封装为 **MCP Server**，这体现了架构的前瞻性和规范性。
5. **不要忽视监控**：金融系统没有监控就是“裸奔”。哪怕只是一个简单的 QPS 曲线，也能体现你的工程素养。
