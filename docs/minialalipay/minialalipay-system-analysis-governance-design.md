# MiniAlalipay 系统分析文档分层与去重设计

## 1. 设计目标

本文明确总体系统分析与后端系统分析的权威边界、引用关系和维护规则，解决两份文档重复描述系统架构、业务流程、状态、接口、数据表和安全规则所产生的内容漂移风险。

本次调整只重构文档组织，不新增或改变产品功能、接口字段、状态流转、数据库表、事件、安全规则或部署依赖。

## 2. 当前问题

`minialalipay-system-analysis.md` 已完整覆盖系统边界、服务职责、领域模型、业务流程、状态模型、数据架构、接口、安全、监控、部署和测试。

`minialalipay-backend-system-analysis.md` 又重复维护了以下事实：

- 服务职责和系统执行链路。
- 限界上下文、聚合和数据所有权。
- 注册、充值、转账、扫码、个人收款和 Mini 花呗流程。
- 交易状态、TCC、一致性和幂等规则。
- 数据表、API 端点、错误码、权限和监控要求。
- 测试策略、需求映射和后端不变量。

同一事实存在两个维护位置，会造成章节版本、接口字段、状态含义、数据约束和测试口径不一致。

## 3. 文档权威层级

项目文档按以下层级管理：

1. `minialalipay-prd.md`：需求与验收事实来源，定义系统需要实现什么。
2. `minialalipay-system-analysis.md`：系统架构事实来源，定义系统边界、职责、流程、状态、不变量和质量要求。
3. `contracts/openapi/minialalipay-api.yaml`：HTTP/SSE 接口路径、方法、字段、响应和协议事实来源。
4. `minialalipay-database-design.md`：物理表、字段、索引、约束和 Schema 所有权事实来源。
5. `minialalipay-backend-system-analysis.md`：后端实现设计，说明上述事实如何映射到 Java 模块、代码、框架、配置和测试。

上述层级不是允许下层覆盖上层。发现冲突时必须停止合并，同步修正相关基线和契约；不得在后端系分或代码中隐藏兼容未说明的行为。

## 4. 总体系统分析职责

总体系统分析继续完整维护以下内容：

- 系统目标、范围、参与者、用例和质量属性。
- 前端、网关、用户中心、业务中心、账户中心和 AI 服务的职责边界。
- 限界上下文、聚合关系、数据所有权和跨服务依赖。
- 注册、充值、转账、扫码、个人收款、信用支付和还款的完整业务流程。
- 订单、交易、TCC、信用、账单、收款请求和告警状态模型。
- 架构不变量、资金一致性、幂等、Saga、Outbox/Inbox 和终态发布规则。
- API 语义、事件语义、错误语义、权限、安全和审计要求。
- 监控、指标、容量、部署、故障恢复、测试和需求追踪。

总体系统分析描述系统事实，不绑定某个 Controller、Mapper、配置类或测试类的具体名称。

## 5. 后端系统分析职责

后端系统分析只保留后端落地内容：

- 当前代码已经实现和尚未实现的基线。
- Maven 模块、Java 包、依赖方向和 ArchUnit 门禁。
- 总体聚合到 Java 聚合根、值对象、领域服务和仓储端口的映射。
- 用例到 Application Service、事务入口和外部端口的映射。
- OpenAPI 操作到 Controller、API DTO、异常转换和生成代码的映射。
- 数据库设计到 PO、Mapper、Repository、Flyway 迁移和本地事务的映射。
- TCC、Saga、Outbox/Inbox、恢复任务和终态发布的框架实现位置。
- Spring Security、网关过滤器、Trace、日志脱敏、配置项和调度任务的位置。
- 单元测试、组件测试、契约测试、集成测试和故障注入测试的代码目录与执行命令。
- 后端开发顺序、发布门禁以及总体规则到代码和测试的追踪矩阵。

后端系统分析不得重新定义业务状态、API 字段、表字段、错误语义或系统安全规则。

## 7. 后端系统分析目标结构

重构后的后端系统分析采用以下结构：

1. 文档定位、权威层级和冲突处理。
2. 当前代码实现基线。
3. Maven 模块、Java 包和依赖门禁。
4. 领域模型的 Java 实现映射。
5. Application Service、事务入口和外部端口。
6. Controller、API DTO、事件与协议适配器。
7. PO、Mapper、Repository、Flyway 和本地事务。
8. TCC、Saga、Outbox、恢复任务和终态发布实现。
9. 安全、权限、Trace、日志、缓存、调度和配置落点。
10. 测试目录、执行命令、开发顺序和发布门禁。
11. 总体系分规则到代码与测试的追踪矩阵。

每一章开头注明对应的总体系统分析、OpenAPI 或数据库设计章节，然后只描述后端实现增量。

## 8. 变更维护规则

### 8.1 只修改总体系统分析的场景

- 系统边界、服务职责、参与者或跨端流程变化。
- 业务状态、资金不变量、安全规则或质量属性变化。
- 尚未涉及具体 Java 落点的架构说明修正。

### 8.2 同时修改总体和后端系统分析的场景

- 新增服务、模块、限界上下文或跨服务事务参与者。
- 总体规则变化导致 Java 包、类、事务、配置或测试落点变化。
- 新增后端部署依赖、框架机制或架构门禁。

### 8.3 只修改后端系统分析的场景

- 在不改变系统行为的前提下调整类名、包名、实现类或配置文件位置。
- 重构 Repository、Adapter、Mapper 或测试目录。
- 更新当前代码完成状态、执行命令或 CI 检查方式。

### 8.4 专项契约同步

- API 方法、路径或字段变化必须修改 OpenAPI；涉及系统语义时同时修改总体系分。
- 表、字段、索引或约束变化必须修改数据库设计；涉及数据所有权或事务边界时同时修改总体系分。
- 后端系分只记录对应 Controller、DTO、PO、Mapper、迁移和测试的落点。

## 9. 冲突处理规则

1. PRD 与总体系统分析冲突时，以需求评审结果为准，并同步修正两份文档。
2. 总体系分与 OpenAPI 或数据库设计冲突时，禁止实现和合并，先统一语义与契约。
3. 后端系分与上层基线冲突时，修正后端系分，不能用实现文档覆盖系统事实。
4. 代码与文档冲突时，代码不得被视为默认事实来源；必须根据已批准基线决定修改代码还是文档。
5. 测试只验证已批准的需求和架构，不得通过改变断言固化错误实现。

## 10. 验收标准

完成重构后必须满足：

- 两份文档都明确总体系统分析是系统架构事实来源。
- 后端系分不存在完整复制的业务流程、状态表、API 目录、数据表目录和系统级安全规则。
- 后端系分中的保留内容可以定位到具体模块、包、类、配置、迁移或测试目录。
- 所有被删除的重复事实都有稳定章节引用，不出现信息丢失。
- OpenAPI 和数据库设计的专项事实来源地位明确。
- 文档内部链接有效，不引用旧文件名或物理行号。
- 文档不存在相互矛盾的版本、哈希或权威声明。
