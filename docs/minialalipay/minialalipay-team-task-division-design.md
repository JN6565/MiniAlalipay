# MiniAlalipay 团队任务分工设计

## 1. 文档目的

本文依据 MiniAlalipay PRD、系统分析和现有单仓库结构，明确五名成员在 P0 功能开发中的任务包、代码所有权、跨模块依赖、评审责任和 Git 协作规则。

本方案按任务和模块边界分工，不按日期安排。目标是减少多人同时修改相同文件，保证业务、资金、AI、前端和测试可以并行开发，并使接口、数据库和系统行为保持一致。

本文只规定团队协作与代码所有权，不新增或改变产品功能、接口字段、状态流转、数据库表、安全规则或部署依赖。

## 2. 分工原则

1. 每个后端服务和前端工程设置唯一最终合入负责人；`business-center` 和 `account-center` 按功能子域包进一步划分代码所有权。
2. 跨模块协作以 OpenAPI、事件 Schema 和统一错误码为边界，不共享持久化对象、Mapper、仓储或领域聚合。
3. 每个任务包必须同时交付实现代码、模块内测试、必要的数据库迁移和相关文档更新。
4. 前端只通过网关访问后端，并使用 OpenAPI 生成的类型和客户端。
5. `business-center` 是全系统业务编排核心，`account-center` 是资金安全核心；两个中心内最关键的交易、余额、TCC 和账本内核统一由王钧平负责，王基哲进行交叉评审和质量验证。
6. 共享热点文件由指定负责人合入，普通业务分支不得顺带修改无关公共配置。
7. 所有成员负责自己模块的单元测试和组件测试，跨服务测试由质量负责人统一维护。

功能子域包的所有权同时覆盖对应 Controller、应用服务、领域模型、仓储实现和模块测试。服务启动类、跨子域配置、公共适配器和 Flyway 迁移目录属于共享热点，由王钧平最终合入；功能负责人仍负责提供自己子域的迁移内容和测试。

共享热点文件的最终合入责任如下：

| 文件或目录 | 最终合入负责人 | 约束 |
|---|---|---|
| `backend/platform-common/` | 王钧平 | 只能增加技术通用类型，禁止加入领域类型 |
| `backend/pom.xml` | 王钧平 | 依赖或构建插件变更必须独立提交 |
| `contracts/` | 王钧平 | 其他模块负责人提出变更，契约合入后再实现 |
| 网关路由配置 | 李思远 | 仅路由到已存在 OpenAPI 操作和已实现 Controller |
| PRD、系统分析和数据库设计 | 涉及模块负责人修改，王钧平复核 | 行为、接口或表结构变化必须同步文档 |

除上表明确拆分的两个核心服务外，其他目录保持单一负责人。任何跨子域或跨目录修改都必须由对应代码负责人审核，并由最终合入负责人合入。

## 4. 个人任务包

### 4.1 王钧平：资金交易内核与契约

负责横跨 `business-center` 和 `account-center` 的资金交易内核。在 `business-center` 中控制业务交易状态和跨服务编排，在 `account-center` 中实现余额、TCC 分支和账本事实；两个服务仍通过公开契约交互，禁止因负责人相同而共享持久化类型或绕过服务边界。

主要 P0 任务：

- 统一资金交易主单、交易类型、状态机和最终状态发布。
- 转账草稿、收款人解析、版本控制、确认令牌、提交和交易回执。
- `source_type + source_order_id` 唯一受理和幂等处理。
- TCC 全局事务发起、Saga 异常补偿、恢复扫描和终态收敛。
- 注册后幂等开户、账户状态、可用余额、冻结金额和余额版本。
- 模拟充值入账、付款冻结与扣款、收款预占与入账、解冻和受控退款。
- TCC Try、Confirm、Cancel 分支屏障、幂等、空回滚和防悬挂。
- 不可变复式账本凭证、借贷分录、平衡校验、冲正和账务修复。
- 资金、信用和 C2C 对账核心规则，以及自动恢复与人工处置的边界判定。
- OpenAPI、事件 Schema、错误码和跨服务请求响应契约。
- `business-center` 和 `account-center` 共享启动配置、公共适配器及 Flyway 迁移的最终合入。

边界约束：

- `business-center` 只能通过账户中心公开 API 或版本化事件请求资金动作，不得导入账户中心的 Mapper、仓储、PO、实体或聚合根。
- 只有 `account-center` 内的资金内核可以修改余额和账本；同一负责人不得把跨服务流程退化成跨 Schema 本地事务。
- 信用额度和应收由王基哲负责的信用子域修改，但必须通过王钧平提供的账户、TCC 和账本应用入口完成资金联动。
- 不得将业务交易终态提前于 TCC 分支和账本事实发布。

### 4.2 李思远：AI 与统一入口

负责 AI 能力和所有外部请求的统一入口，不持有资金执行权限。

主要 P0 任务：

- AI Talk 多轮会话、意图识别、槽位补全和上下文压缩。
- 转账、余额、交易、联系人、信用额度和账单等结构化意图。
- Agent 结果解释、工具调用摘要、Schema 校验和失败降级。
- MCP 工具目录、协议适配、工具风险等级和策略网关。
- 提示注入防护、敏感信息脱敏、越权工具拦截和审计记录。
- 网关鉴权、路由、限流、请求编号、安全响应头和统一异常处理。
- `X-Request-Id` 生成与透传，以及 AI 到业务服务的完整 Trace。

边界约束：

- AI 只能理解、查询、创建或校验业务草稿，不直接扣款、入账或记账。
- MCP 工具只能调用网关或公开契约，不访问服务数据库。
- 网关不得承载领域规则或修改业务响应中的资金事实。

### 4.3 闫泽华：用户体系与 C 端

负责用户身份上下文及面向普通用户的 H5 交互。

主要 P0 任务：

- 用户注册、登录、退出、会话校验和角色识别。
- 登录密码、支付密码、错误次数、锁定和安全校验。
- 用户搜索、常用联系人、收款人别名和模拟实名信息。
- H5 登录、首页、传统转账、交易结果和交易记录页面。
- H5 动态扫码付款、个人码付款、固定金额请求付款页面。
- 个人收款码、固定金额收款请求和跨端状态页面。
- 余额、收支明细、Mini 花呗额度、账单和还款页面。
- OpenAPI 客户端接入、TanStack Query 缓存和路由级拆包。

边界约束：

- H5 只调用 `http://localhost:8080` 网关地址。
- Zustand 只保存客户端 UI 状态，不复制余额、账本事实或交易终态。
- 支付密码、确认令牌和二维码原始令牌不得进入浏览器存储、埋点或 URL。

### 4.4 王春桂：交易场景与 B 端

负责 `business-center` 的外围交易场景子域和 B 端运营维护页面。B 端只面向运营、管理员和观察者，不承载普通用户收款业务；动态扫码收款、本人订单和本人统计页面由 C 端负责人实现，本任务包提供相应业务接口。场景子域只能调用王钧平维护的统一交易和资金应用接口，不直接改变资金事实或自行发布交易终态。

主要 P0 任务：

- 模拟充值规则、每日限额、充值订单、退款订单和模拟渠道结果。
- 普通用户动态扫码收款订单、二维码原始令牌保护、令牌交换、订单 CAS 和服务端状态推送。
- 长期个人收款码、固定金额收款请求、单次收款订单和多付款尝试仲裁。
- 基础风控、人工确认工单、异常状态和运营处置接口。
- 监控投影、告警、运营查询和 T+1 数据质量展示接口。
- 为 C 端提供扫码收款订单创建、动态二维码、本人订单状态查询接口。
- 为 C 端提供扫码收款结果 SSE 更新、断线重连和轮询兜底接口。
- 为 C 端提供本人扫码收款、订单和支付方式统计接口；B 端仅展示全平台脱敏聚合指标。
- 异常订单、人工确认工单和处置记录页面。
- 交易链路、实时指标、告警、恢复任务和对账结果看板。
- 用户、角色、演示配置和规则管理页面。
- B 端权限控制、路由级拆包、OpenAPI 客户端和请求编号透传。

边界约束：

- 运营页面不能直接修改余额、账本、信用额度或交易终态。
- 场景子域不得自行实现余额扣减、账本写入或另一套交易状态机。
- 场景进入资金执行前必须使用已合入的确认、交易和 TCC 应用接口。
- 所有处置操作必须调用有审计记录的业务接口。
- 页面只展示服务端确定的状态，未知结果不得显示为成功。

### 4.5 王基哲：信用业务与质量保障

负责 `account-center` 的信用、账单和还款子域，以及跨服务质量门禁。资金余额、TCC 分支和账本公共内核由王钧平提供，王基哲负责以模块测试和故障注入验证其正确性。

主要 P0 任务：

- Mini 花呗固定额度、额度冻结、信用应收、消费明细和账单。
- 提前、部分、全额还款，分配顺序、逾期暂停和清偿恢复。
- 信用支付和还款对账户、TCC、账本内核的应用接口适配。
- 信用子域 Flyway 迁移内容和账户、账本数据库设计同步，由王钧平最终合入迁移文件。
- API、E2E、性能、故障注入、安全和跨服务集成测试。
- 重点覆盖余额并发、TCC 重试、空回滚、悬挂、重复提交、账本平衡和终态发布。
- MySQL、Redis、Seata 和可观测组件的本地部署配置。

边界约束：

- 只有账户中心可以修改余额、信用额度、账本凭证和账本分录；信用子域不得绕过账户和账本应用入口直接修改余额表或分录表。
- 账户中心不创建业务交易主单，也不自行决定业务订单终态。
- 账本修复只能通过新冲正分录完成，不修改或删除原分录。

## 5. 任务依赖与交付顺序

以下是任务依赖和开发闸门，不是时间排期。未满足当前阶段的交付条件时，任何成员不得超前进入后续阶段；确需并行时，只能使用已冻结的契约或 Mock，不得自行发明接口和状态。

### 5.1 阶段一：基础契约和工程基线

**负责人及复核人：** 王钧平。

**交付内容：** 统一术语、ID、金额、时间、状态和版本规则；冻结 OpenAPI 公共响应、请求头、鉴权和 P0 接口目录；完成错误码契约、事件 Envelope、事件版本和幂等键规则；完善 `platform-common` 技术通用类、全局异常转换和请求编号约定。

**进入条件：** OpenAPI、错误码和事件契约已经合入，公共类测试通过。未满足条件时，其他成员不得开发依赖这些契约的真实接口。

**当前验收状态（2026-08-03）：已完成并关闭。** 王钧平负责的公共响应、请求头、鉴权、P0 接口目录、错误码、事件 Envelope、事件版本、幂等规则和 `platform-common` 公共能力已完成并通过本人复核，公共类测试和阶段一契约校验通过。P0 目录不等于业务操作完整 Schema，各业务 Controller 仍须按纵向切片先补对应 OpenAPI 操作。

### 5.2 阶段二：服务骨架和网关链路

**负责人：** 各服务负责人；李思远负责网关，王钧平负责共享配置最终合入。

**交付内容：** 五个 Spring Boot 服务独立启动并通过健康检查；网关完成鉴权入口、路由、`X-Request-Id` 透传、统一异常和基础限流；各服务完成分层空壳和最小契约测试。

**进入条件：** 网关到各服务的健康检查和错误响应测试通过。前端只能使用网关地址，不能直连服务端口。

**当前验收状态（2026-08-03）：王钧平负责部分已完成，阶段二整体未关闭。** `business-center` 和 `account-center` 已具备独立启动配置、健康检查、四层及本人负责子域的目录说明、统一错误响应、HTTP 协议错误码及请求编号处理，并通过服务启动、异常响应和架构边界测试；父 POM、公共错误码契约和两服务共享配置已由王钧平合入。网关鉴权、路由、限流以及网关到服务的链路验收仍由李思远负责，完成前不得将阶段二整体标记为关闭。

### 5.3 阶段三：用户、账户和数据基础

**负责人：** 闫泽华负责用户中心，王钧平负责账户和账本内核，王基哲负责信用基础和质量门禁。

**交付内容：** 完成用户注册、登录、会话、支付密码、账户开户、余额冻结、版本控制、账本凭证和信用基础模型；各服务完成自己的 Schema、Flyway 迁移和模块测试。

**进入条件：** 用户身份、账户余额和账本不变量测试通过；只有账户中心能够修改余额和账本；信用子域不得绕过资金入口。

### 5.4 阶段四：统一交易内核

**负责人：** 王钧平；王基哲负责并发和故障交叉验证。

**交付内容：** 完成转账草稿、确认、版本冲突、统一交易主单、来源唯一、幂等、状态机、TCC分支、空回滚、防悬挂、终态发布、恢复扫描和对账核心。

**进入条件：** 普通转账主链路可以从网关完成；重复请求、余额不足、Confirm超时、Cancel重试、服务重启和账本不平测试通过。未通过时，不得开发依赖资金执行的扫码、C2C或AI提交工具。

### 5.5 阶段五：业务场景子域

**负责人：** 王春桂负责充值、扫码、个人码、固定请求、风控、工单和监控；王基哲负责信用、账单和还款。

**交付内容：** 场景对象只负责业务入口、并发仲裁和状态投影；所有资金执行统一调用阶段四的交易、确认和TCC应用接口；B端运营接口增加权限、审计和未知状态展示规则。

**进入条件：** 每个场景具备模块测试、错误码和迁移；场景不得创建第二套扣款逻辑、交易状态机或终态发布逻辑。

### 5.6 阶段六：AI、前端和运营页面

**负责人：** 李思远负责AI和MCP；闫泽华负责H5；王春桂负责B端。

**交付内容：** AI实现会话、意图、槽位、Memory和MCP工具；H5和B端基于已冻结OpenAPI实现页面。前端可提前使用OpenAPI Mock，但不得复制后端DTO或资金状态。

**进入条件：** 前端和AI均能通过网关访问真实接口；确认令牌、支付密码和二维码原始令牌未进入日志、URL、浏览器存储或AI消息。

### 5.7 阶段七：跨服务联调和发布门禁

**负责人：** 王基哲牵头，所有模块负责人参加。

**交付内容：** 完成API契约、E2E、性能、故障注入和安全测试；覆盖重复提交、并发冻结、TCC重试、未知结果、Redis/Outbox不可用、服务重启和对账修复；从H5、B端和AI入口统一经网关验证完整链路。

**最终门禁：** 阶段七通过后才允许合并P0完整功能。任何只通过单服务测试、未完成跨服务测试的功能，不得标记为完成。

### 5.8 超前开发限制

1. 契约未合入前，不得实现依赖该契约的真实Controller、前端客户端或MCP工具。
2. 统一交易和账户应用接口未完成前，场景负责人只能完成领域草图、Schema、Mock和非资金页面，不得写扣款、入账或账本逻辑。
3. 网关路由只能指向已经存在且通过测试的接口，不得先配置预留路由冒充已实现能力。
4. 前端可以并行做页面结构和Mock，但真实接口合入后必须完成一次契约替换和联调。
5. 每个阶段只能合入本阶段及其前置阶段的文件；跨阶段修改必须在PR中说明依赖和复核人。

跨模块功能以契约和测试作为交接物，不以口头说明或直接共享 Java 类作为交接物。

## 6. Git 分支与提交规则

### 6.1 分支粒度

采用一个任务包一个短分支，不建立个人长期开发分支，不允许多人直接向主分支提交。

分支示例：

- `feature/business-transfer`
- `feature/business-qrpay`
- `feature/business-collection`
- `feature/account-ledger`
- `feature/account-credit-bill`
- `feature/ai-agent-session`
- `feature/user-auth`
- `feature/h5-qr-payment`
- `feature/admin-monitoring`
- `test/transaction-fault-injection`
- `fix/account-tcc-idempotency`

### 6.2 提交格式

提交使用 `type(scope): 中文简洁说明`，例如：

```text
feat(transaction): 增加转账幂等受理
test(account): 覆盖重复确认记账场景
fix(gateway): 修复请求编号未透传问题
```

一次提交只包含一个完整变更，公共配置、格式化、业务行为、数据库迁移和契约修改不得无关混合。

### 6.3 共享热点文件

以下修改必须建立独立 PR：

- `backend/pom.xml`
- `backend/platform-common/`
- `contracts/`
- 网关路由配置
- 公共前端请求封装
- `deploy/docker-compose.yml`

业务功能需要公共能力时，先合入公共能力或契约 PR，再开发依赖该能力的业务 PR。

## 7. 数据库协作规则

1. 每个服务只修改自己拥有的 Schema。
2. 功能子域负责人编写本子域迁移内容；`business-center` 和 `account-center` 的迁移文件由王钧平最终审核和合入。
3. 创建迁移前登记完整文件名，避免时间戳和名称冲突。
4. 已合入或已执行的 Flyway 文件不得修改、删除或重命名。
5. 修正数据库问题必须新增向前迁移。
6. 业务中心迁移不得修改账户、账本、信用或用户表。
7. 账户中心迁移不得创建交易主单、用户、Agent 或业务订单表。
8. 涉及金额、账户、账本、TCC、交易或事件表时，必须同步数据库设计、系统分析和集成测试。

## 9. 合并门禁

每个 PR 合并前必须确认：

- 当前模块单元测试和组件测试通过。
- 接口实现与 OpenAPI 一致。
- 涉及数据库时，Flyway 迁移和数据库设计一致。
- 涉及系统行为变化时，PRD 或系统分析已同步。
- 金额字段统一使用整数 `amountFen`，后端使用 `long` 分。
- 写操作使用服务端定义的幂等键。
- 日志、URL、浏览器存储和埋点不包含支付密码、确认令牌或二维码原始令牌。
- 未直接访问其他服务的数据库或内部持久化类型。
- 未包含其他负责人目录中的无关修改。
- 交易未知时没有提前展示或发布成功。
- 资金成功时存在借贷平衡分录，并覆盖 TCC、幂等和对账测试。

## 10. 冲突处理规则

1. 代码冲突由冲突文件的目录负责人处理，功能发起人提供业务意图说明。
2. 接口理解冲突以已合入 OpenAPI 和系统分析为准；需要改变契约时先修改契约，不在代码中兼容未说明行为。
3. 状态含义冲突以业务中心交易状态机为准，资金事实以账户中心账本和余额版本为准。
4. 前端展示与后端状态不一致时，前端不得自行推断终态，应由后端契约明确展示状态。
5. 测试与实现不一致时，先核对 PRD 验收条件；不得仅为通过测试而削弱业务不变量。
6. 同一共享文件存在两个并行修改时，暂停后发分支，由该文件负责人先合入基础变更，其他分支同步后继续。

## 11. 任务完成定义

一个任务包只有同时满足以下条件才算完成：

1. 需求编号和验收条件明确。
2. 生产代码已经实现。
3. 模块内测试已经通过。
4. OpenAPI、事件和错误码与实现一致。
5. 必要的数据库迁移和数据库设计已经完成。
6. 错误处理、请求编号、日志脱敏和审计字段已经覆盖。
7. 跨服务任务已经加入集成测试或 E2E 测试。
8. 涉及资金时已经验证幂等、TCC、复式记账、恢复和对账。
9. PR 已由目录负责人及必要的交叉复核人批准。

## 12. 执行结论

本方案把交易状态机、账户余额、TCC 和复式账本等最核心、最困难的资金交易内核统一交由王钧平负责；业务中心和账户中心仍保持独立服务、数据和契约边界。其他成员按交易场景、信用业务、用户与 C 端、AI 与网关划分任务，以功能子域包所有权和唯一最终合入负责人降低代码冲突，并由王基哲统一跨服务测试和故障注入，保证 P0 主链路形成完整、可验证的交付。
